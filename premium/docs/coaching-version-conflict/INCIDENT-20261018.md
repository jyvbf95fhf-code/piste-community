# Arrêt ciblé de la boucle PostgREST — 18 octobre 2026

Projet exclusif : shnwqdkiapgcftbnhilh. Base applicative : b85422c.

## Cause démontrée

Les erreurs SQLSTATE 40001/version_conflict de public.coaching_commit étaient produites par deux backends PostgREST 14.18, PID 76571 et 76572, ouverts le 15 octobre à 17:03:45 et 17:03:46 UTC. Entre 13:59 et 14:02 UTC, ils représentent à eux seuls 17 997 erreurs. Aucun processus QA Node/Python/Deno actif identifié dans le conteneur accessible ; les retries applicatifs examinés sont bornés. Aucun flux HTTP achevé correspondant dans les sources disponibles sur cette fenêtre.

Le comportement correspond au défaut PostgREST 14 documenté officiellement : utiliser SQLSTATE 40001 pour un conflit métier déclenche des retries transactionnels infinis. Ce ne sont donc pas nécessairement des milliers de nouveaux appels émis par un robot. L'appelant initial des deux appels anciens ne peut pas être attribué avec les logs disponibles ; aucun compte ou navigateur n'a été désigné sans preuve.

Source officielle : https://supabase.com/docs/guides/troubleshooting/high-cpu-and-infinite-transaction-retries-when-using-custom-error-codes-in-rpc-functions-77326b

## Intervention effectivement appliquée

Le 18 octobre à 14:04:03.595 UTC : terminaison des **deux backends identifiés uniquement**, avec garde sur PID, rôle authenticator, application PostgREST 14.18, base courante et date de démarrage exacte. Les deux appels pg_terminate_backend ont renvoyé true. Aucune terminaison générale ni redémarrage du projet.

```sql
select a.pid,a.backend_start,pg_terminate_backend(a.pid) as stopped
from pg_stat_activity a
where a.datname=current_database()
and a.pid in (76571,76572)
and a.usename='authenticator'
and a.application_name='PostgREST 14.18'
and a.backend_start between '2026-10-15 17:03:44+00'::timestamptz
                         and '2026-10-15 17:03:48+00'::timestamptz;
```

Une première tentative avec garde sur requête/état instantané n'a sélectionné aucune ligne : ces champs alternaient rapidement entre exécution, configuration de transaction et état aborté. Aucun backend n'a été arrêté par cette tentative.
