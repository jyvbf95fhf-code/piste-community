# V10.44 — Spécification fonctionnelle

## 1. Entrée Centre Admin
Ajouter un accès "Admin" visible uniquement pour le compte administrateur autorisé.
L’entrée doit être absente pour les utilisateurs standards.
La capacité admin doit être vérifiée côté serveur/base, pas seulement dans le front.

## 2. Dashboard
Créer des KPI compacts :
- Utilisateurs totaux
- Nouveaux utilisateurs sur 7 jours
- Nouveaux utilisateurs sur 30 jours
- Utilisateurs actifs récemment
- Nombre total de pistes
- Répartition OPS / Entraînement / Coaching
- Retours / idées non lus
- Activité récente

Ne pas inventer de métriques impossibles à calculer.
Si "utilisateur actif" doit être défini, documenter précisément la règle.

## 3. Nouveaux utilisateurs
Afficher :
- nom / pseudo si disponible ;
- email uniquement si déjà autorisé et utile ;
- date de création ;
- date de dernière activité ;
- statut du compte si disponible ;
- bouton "Voir le profil admin".

Tri par plus récent par défaut.

## 4. Utilisateurs
Créer :
- recherche ;
- filtres ;
- tri ;
- liste compacte mobile.

Recherche :
- nom ;
- pseudo ;
- email si sécurité et données existantes le permettent.

Filtres utiles :
- actif récemment ;
- inactif ;
- date d’inscription ;
- type d’usage dominant ;
- a envoyé un retour ;
- a créé une session récemment.

## 5. Fiche utilisateur Admin
Afficher uniquement les infos utiles :
- identité publique / compte ;
- date d’inscription ;
- dernière activité connue ;
- nombre de sessions ;
- nombre OPS ;
- nombre Entraînement ;
- nombre Coaching ;
- distance cumulée si calculable proprement ;
- dernière session ;
- retours / idées envoyés ;
- activité récente.

Éviter les données privées inutiles.

## 6. Activité récente
Timeline alimentée uniquement par des événements réellement observables :
- nouveau compte ;
- nouvelle piste ;
- session Coaching créée ;
- session terminée ;
- retour utilisateur envoyé.

Chaque événement :
- date/heure ;
- utilisateur ;
- type ;
- contexte court ;
- lien pertinent si autorisé.

## 7. Statistiques globales
Créer :
- utilisateurs totaux ;
- nouveaux utilisateurs par période ;
- actifs 7j / 30j ;
- nombre de pistes ;
- OPS / Entraînement / Coaching ;
- sessions terminées ;
- distance cumulée si fiable ;
- activité sur 7 / 30 / 90 jours.

Graphiques simples et mobile-first uniquement si utiles.

## 8. Retours / idées / améliorations
Créer une boîte de réception Admin pour "J’ai une idée / amélioration".

Chaque retour :
- auteur ;
- date ;
- sujet ;
- message ;
- contexte de page/module si facile à capturer sans intrusion.

Statuts :
- Nouveau
- Lu
- À traiter
- Traité

Fonctions :
- ouvrir ;
- changer statut ;
- filtrer ;
- rechercher ;
- voir l’auteur.

## 9. Design
Style :
- dark premium ;
- mobile first ;
- cartes compactes ;
- indicateurs lisibles ;
- navigation simple.

Navigation :
- Tableau de bord
- Utilisateurs
- Activité
- Statistiques
- Retours

## 10. Sécurité
- autorisation Admin côté serveur ;
- pas de fuite de liste utilisateurs ;
- pas de lecture brute non filtrée de données sensibles ;
- conserver les RLS existantes ;
- `security definer` uniquement si nécessaire, avec `search_path=''` et contrôles explicites ;
- permissions minimales ;
- aucune policy permissive globale.

## 11. Compatibilité
Ne pas casser :
- V10.43 Mes pistes / Dossier de mission ;
- Coaching V10.42.3 ;
- OPS ;
- Entraînement ;
- auth ;
- profils / amis.

## 12. SQL
Audit obligatoire avant migration.
Si l’existant suffit : SQL = NON.
Sinon préparer seulement :
- `PISTE_V10.44_PATCH/PISTE_V10.44_DRY_RUN.sql`
- `PISTE_V10.44_PATCH/PISTE_V10.44_APPLY.sql`
- `PISTE_V10.44_PATCH/README_SQL.md`

Ne jamais exécuter le SQL automatiquement.
